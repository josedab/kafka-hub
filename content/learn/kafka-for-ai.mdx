Kafka can make an AI system easier to recover and operate when it carries
durable facts: source changes, work intents, result references, evaluations,
and audit events. It does not become a model runtime, tool registry, agent task
protocol, or synchronous chat path merely because those systems emit events.

This is the entry point for the **Kafka for AI Engineers** track. The track
keeps a narrow division of responsibility:

| Boundary | Owns |
| --- | --- |
| Kafka | Durable ordered transport, retention, replay, independent fan-out |
| Model/vector/tool systems | Inference, vector writes/search, authorization, external-effect contracts |
| MCP | JSON-RPC lifecycle and tools/resources/prompts/context exchange |
| A2A 1.0 | Agent discovery plus message/task/artifact interoperability |

It assumes you already understand topics, partitions, and consumer groups at
the level of [ISR & acks](/learn/isr-and-acks) and
[consumer rebalances](/learn/consumer-rebalance).

## Durable pattern 1 — RAG ingestion pipelines

The "embed everything in our document corpus" pipeline is the canonical fit:

```
docs.ingest  →  embedder workers  →  embeddings.results  →  vector sink
   (raw text)     (call OpenAI/etc)     (vector + metadata)     (Pinecone, pgvector)
```

Why Kafka, rather than an untracked one-shot loop:

- **Back-pressure for free.** If the vector sink slows down, the embedder
  workers' commit lag grows but they keep working through the topic at
  their own pace. No retry storms.
- **Replay.** When you change an embedding model, re-read a bounded, versioned
  source stream and write to a candidate index/result topic. Do not overwrite
  the only serving index without comparison and rollback.
- **Fan-out.** Add a `summaries.results` consumer that reads the same
  `docs.ingest` topic in a different group. Costs nothing on the producer
  side.

Try it below — turn up the embed latency and watch lag grow. Then continue with
[streaming RAG freshness](/learn/streaming-rag-freshness) for source/index
versions, CDC tombstones, backfills, and a measurable stale window.

### Partition key strategy for RAG

Pick a key that aligns with **what stays together logically** for downstream
consumers. Two patterns that work:

- **Key by document id** — every chunk of a document goes to the same
  partition. The embedder sees them in order, which lets you do
  context-window-aware embedding (chunk N has access to chunk N-1).
- **Key by tenant id** — multi-tenant RAG. All chunks for tenant T land in
  the same partition, simplifying reasoning about per-tenant rate limits.

Anti-pattern: key by chunk id (effectively random). You lose any per-doc or
per-tenant locality and add no benefit.

### Producer config for embedding pipelines

- `acks=all`, `enable.idempotence=true` — the embedder is going to call an
  expensive remote API; you cannot afford to lose ingest events.
- `compression.type=zstd` — text payloads compress fantastically and you
  pay the network cost on every read by every embedder.
- `batch.size=131072`, `linger.ms=20` — text-ingest workloads are
  throughput-bound, not latency-bound.

### Consumer config for embedding pipelines

- `max.poll.interval.ms` should be **larger than your slowest model call**
  by a comfortable margin. The default 5 minutes is fine for OpenAI; bump
  it for self-hosted models that may stall on a cold start.
- `max.poll.records=1` or low single digits, **if** each record triggers a
  blocking model call. Otherwise you'll burn the entire batch on one
  timeout and rebalance.

## Durable pattern 2 — observable agent execution events

An agent should produce observable operation events—tool requests/results,
retrieval references, guardrail/evaluation outcomes, status changes, retries,
and final artifacts. Treating each run as only a final “done” row throws away
the evidence needed for debugging, evaluation, cost control, and incident
recovery.

A trace-as-topic pattern:

```
agent-events.v1   topic, key=run_id, ordered event timeline
agent-state.v1    compacted topic, key=run_id, latest safe status
agent-evals.v1    topic, key=run_id, versioned evaluator outcomes
```

The producer writes observable facts at each operation boundary. Downstream
consumers can build a trace UI, evaluation store, audit archive, or aggregate
metrics independently. Do not stream hidden chain-of-thought or unbounded raw
prompts/tool payloads; redact at collection and use access-controlled
references for larger sensitive data.

Use a compacted state topic for the current review verdict and retain an
append-only evaluator event history when auditability requires it. A later
human review should be a new observed event, not a mutation that erases why an
earlier decision happened.

## Durable pattern 3 — online feature pipelines

For ML systems that need fresh features at inference time (recommendations,
fraud, ranking), Kafka in front of an online feature store is the standard
pattern.

```
events  →  feature.computed  →  feature store (Redis/Aerospike/Cassandra)
                ↓
            offline DWH for training
```

The useful property is that the same versioned event contract can drive both
the online store (low-latency point lookups) and the offline warehouse
(joinable batch). That helps teams reason about train/serve alignment, but it
does not make independently operated materializations automatically consistent.

The important property is a replayable event contract and explicit materialized
state—not a claim that any two online/offline stores are automatically
consistent.

## Choose a different boundary when Kafka is not the answer

- **Tool/resource discovery:** use
  [MCP](https://modelcontextprotocol.io/docs/learn/architecture), whose
  JSON-RPC client/server protocol exposes lifecycle, tools, resources, prompts,
  and context exchange.
- **Cross-agent task interoperability:** use
  [A2A 1.0](https://a2a-protocol.org/latest/specification/) for Agent Cards,
  messages, tasks, artifacts, and updates between independent agents.
- **Interactive request/response:** use a direct authenticated API on the user
  path. Emit durable events around it only when replay/fan-out is needed.

Read [Kafka, MCP, and A2A](/learn/kafka-mcp-a2a) for composition choices.

## When **not** to use Kafka in your AI stack

- **Synchronous chat agents.** A user is waiting for an answer. Kafka adds
  latency and failure modes to a path that should be direct. Use Kafka for
  durable audit/evaluation events, not the chat response itself.
- **Single-model embedding job that runs once.** A Python script with
  `concurrent.futures` is faster to write and runs in 10 minutes. Don't
  build a streaming platform for a one-shot.
- **You don't have operational capacity for Kafka.** Running a stable cluster
  is real work. A managed service may change that trade-off, but it does not
  remove schema, retention, privacy, or recovery design.
