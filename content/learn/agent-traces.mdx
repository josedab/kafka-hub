An agent run is an event timeline, not a final answer row. Kafka can retain and
fan out the observable operational facts needed to debug, evaluate, and audit a
run: status changes, retrieval references, model/tool calls, retries,
guardrail decisions, costs, latency, and final artifacts.

It should **not** become a repository for hidden chain-of-thought, unrestricted
prompts, raw tool payloads, or customer data that has no retention/access
contract.

## One event timeline, keyed by run ID

Start with one append-only topic for a run timeline. Key every event by
`agent_run_id`; Kafka only orders records within a partition, so a stable
run key is what makes per-run reconstruction deterministic.

```json
{
  "agent_run_id": "run_01HZY",
  "seq": 42,
  "kind": "tool_result",
  "ts": "2026-07-26T15:03:11Z",
  "tool_name": "knowledge-search",
  "status": "ok",
  "input_ref": "restricted://trace-inputs/run_01HZY/42",
  "result_ref": "restricted://trace-results/run_01HZY/42",
  "latency_ms": 184,
  "correlation_id": "corr_a4f9"
}
```

Useful `kind` values are observable operations, not private reasoning:

```text
run_started | retrieval | model_request | model_response | tool_request
tool_result | retry | guardrail | evaluation | artifact | run_finished | error
```

The `seq` field is application-level diagnostic evidence. Do not assume it can
replace Kafka's per-partition ordering; validate it and emit an error event if a
producer observes a gap it cannot explain.

## Topic layout and retention

```properties
# Complete ordered timeline per run
agent-events.v1.cleanup.policy=delete
agent-events.v1.retention.ms=604800000
agent-events.v1.partitions=96
agent-events.v1.replication.factor=3

# Latest safe state per run
agent-state.v1.cleanup.policy=compact
agent-state.v1.min.cleanable.dirty.ratio=0.2
agent-state.v1.segment.ms=21600000

# Versioned outcome and evaluation stream
agent-events-eval.v1.cleanup.policy=delete
agent-events-eval.v1.retention.ms=7776000000
```

Separate topics by purpose, retention, and access policy—not merely by event
kind. Operational traces may expire quickly. Evaluator outcomes may need a
longer, tighter-controlled retention period. A compacted state topic answers
“what is safe to show as current?” without scanning the complete timeline.

Use one schema version strategy and include the prompt, model, retrieval-index,
tool, guardrail, and evaluator versions as fields or references. When schemas
change, consumers must tolerate versioned events rather than assume every
historic record has today's fields.

## Partition by run ID, watch hot runs

```ts
producer.send({
  topic: "agent-events.v1",
  key: event.agent_run_id,
  value: JSON.stringify(event),
});
```

This gives ordered replay for one run and scales across runs. If one run emits
millions of operations, it is a hot key. Split its work into explicitly named
phases or introduce a different correlation model; silently changing keys
mid-run destroys the simple reconstruction guarantee.

## Fan-out into state, evaluation, and audit

```text
agent-events.v1
  ├─ state writer       → agent-state.v1 (compacted)
  ├─ evaluation worker  → agent-events-eval.v1
  ├─ trace viewer       → controlled read model
  └─ audit archive      → retention-managed evidence store
```

Each consumer group owns its own offsets and replay policy. The evaluator can
wait for `run_finished`, join observed retrieval/tool/model events by
`agent_run_id`, and score groundedness, policy compliance, tool error rate,
cost, latency, and a human-review verdict. It should retain result references
instead of duplicating sensitive text.

## Align with OpenTelemetry without duplicating everything

The GenAI semantic conventions now live in the dedicated
[OpenTelemetry semantic-conventions-genai repository](https://github.com/open-telemetry/semantic-conventions-genai).
Use trace/span IDs and a correlation ID to connect distributed traces to Kafka
events. Emit the Kafka event as durable evidence of an operation transition;
emit OTel spans/metrics for request-level latency and operational telemetry.

Useful fields include:

- provider, model, route, status, latency, tokens, and cost;
- retrieval query/reference IDs, corpus/index version, result count, and
  freshness;
- tool name, authorization result, retry count, effect-key hash, and result
  reference;
- guardrail/evaluator version, decision/verdict, and human-review reference.

Avoid storing raw hidden reasoning. The information necessary to troubleshoot a
tool call is its request class, authorization outcome, input/result reference,
error, latency, retry, and durable effect result—not private intermediate text.

## Privacy, redaction, and retention are data-plane requirements

- **Minimize at source.** Redact or tokenize sensitive fields before producing
  a trace event; do not rely only on a downstream sink filter.
- **Reference large data.** Store screenshots, PDFs, tool payloads, and long
  model inputs/outputs behind access-controlled object references with
  integrity/version metadata.
- **Separate access.** Keep operational trace readers from automatically
  reading source documents or customer data.
- **Set deletion boundaries.** Compacted state can be tombstoned, but raw
  delete-retained event topics need retention and deletion workflows that match
  policy obligations.
- **Cap volume.** Enforce producer payload limits and record a sanitized
  truncation/error event when a trace is too large.

## Replay and debug

To reconstruct a run, consume the partition that contains its run key and
replay the observable timeline in order. Production debugging should use a
bounded consumer/seek rather than a broad terminal pipeline over all records.
Correct bad state by writing a new observable event; do not mutate history.
